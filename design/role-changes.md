# Role changes

The design, reviewed until it converged: admins and AI assistants give a role to members, or take it away, from one member to thousands, such as "take Friends from everyone who has Clan Member".

## Why

- teabot's roles plugin offers role pickers, which members press to give themselves a role. Nothing lets an admin, or an assistant acting for one, change other members' roles.
- Discord changes one member at a time, so a change to fifty members is fifty clicks.

## The split

The SDK gets what any plugin changing roles needs, the core gets what any long change acting for a member needs, and the roles plugin gets the feature.

### In the SDK

- **`ctx.members`**, the member directory's typed API for plugins ([member-directory.md](member-directory.md#plugins)), built as part of this work, small: `count(filter)` and `find(filter)`, which pages by user ID, behind `Plugin(..., reads=["members"])`, in actions and in jobs. Discord cannot answer "who has this role" without paging every member, which teabot never does in memory (D25), so the directory answers it. Without a ready directory (D55) it raises `DirectoryUnavailable`, with the directory's state.
- **`MemberFilter`, one flat model of D29 input types** (`RoleRef` lists, `str` days, literals, booleans), since plugins import only the SDK: `roles_any`, `roles_all`, `roles_none`, `no_roles`, joined and created ranges, join method, invite and inviter, boosting, timed out, pending, and `bots`, `true`, `false` or null for both, as `admin.members` takes it today. It replaces the core's query dataclass as the query builder's input. `admin.members` takes it and adds its own `name`, `status`, the left ranges, `sort`, `group_by` and `page`, so its callers see no change. A change's filter is a subclass whose `bots` defaults to `false`, people only.
- **A model as an action's input (D29).** An action parameter whose type is a model of D29 fields, such as `filter: MemberFilter`, is flattened into its fields on every front door, slash commands, MCP, the service API and the site's forms, and handed to the function as the model. Its field names must not clash with the action's other parameters or with `confirm`, which registration checks. Its fields' descriptions come from the model, not the function's docstring.
- **`Diff.notes`:** `UntrustedText` lines a plan shows above its entries and never hashes, such as what a role grants, counts and an estimate.
- **Changing a member's role by ID.** `ctx.guild.add_role(user_id, role, by=)` and `remove_role(...)` change a member the bot has not cached with one request. Discord's "unknown member" and "unknown user" errors, codes 10007 and 10013, raise `MemberGone` (S10); every other failure, an unknown role (10011) among them, raises as it does today.
- **`by=`: acting for a member.** `add_role` and `remove_role`, on a `Member` and by ID, take `by=`, a `Member`, resolved once by the caller. Besides the bot's own limits (@everyone, a managed role, a role at or above the bot's highest, the bot's Manage Roles), they then refuse, unless `by` owns the server:
  - `by` without Manage Roles or Administrator;
  - a role at or above `by`'s highest role;
  - for giving only, a role whose server permissions include one `by` lacks, from their roles, with Administrator holding every permission. This is stricter than Discord, on purpose: nobody hands out Administrator through the bot without having it. It reads server permissions only; a permission a role gains through a channel's overwrite is not checked, a gap the pickers' rule shares, accepted. Taking a role away is not checked this way, though it can give access back, such as taking a Muted role; the position rule still applies.
- **`ctx.guild.can_assign(role, by=, give=)`** runs the same check without changing anything, so a plan refuses before confirm. Discord compares only the role's position, never the target member's, so no target is refused for their rank. The pickers use the same check for who may offer a role, and keep their own rule on top: a picker never offers a role with a dangerous permission.
- **The audit reason, extended.** The SDK already writes Discord's audit reason, "via teabot: <action>, for member <id>", or "for teabot" for the bot itself (`_reason` in `sdk/authoring.py`), naming a job's `started_by`. With `by=`, it names `by`, since one job can work through several members' changes. A plugin's `reason=` follows, "...: <reason>", rather than replacing it, so the anchored match below never reads it; the whole is cut to Discord's 512 characters. The directory's match is anchored, `^via teabot: [^,]+, for (member (\d+)|teabot)(: |$)`, and credits the named member only when Discord says the bot made the change (D55). Plugin code runs in the core's process (D5), so this guards against mistakes, not a hostile plugin.
- **A grant: the apply's audit row.** That row names the member, the token if any, the door and the action (D24). An apply reads its ID as `ctx.audit_id`, and the plugin stores it with what it will do later. A job checks it with `await ctx.authorized(audit_id)`, through the same checks the core gives a call (D17 to D20): the row is an apply of this server's and this plugin's action, recorded as handed off; the plugin is still enabled in the server, so turning it off stops the work at its next run; the member is still in the server with the action's `needs`; a token is still valid, within its maximum risk and allow-list. A site sign-in that has since ended does not matter, since the member confirmed the change. It returns the grant's `Actor`, the member, the door and the token, or raises `NotAuthorized` with the reason. A job that checks no grant runs as today, so a poll still closes after its creator's token expires.
- **Handed off, then an outcome.** An apply that hands work off returns `HandedOff(id, text)`, an SDK type, and the core records the apply's outcome as "handed off", not "ok". The name stays clear of the core's `Queued`, which a confirm returns for its apply job. `await ctx.record_outcome(audit_id, text)`, once per handed-off apply, adds an audit row linked to it, which `core.post_audit` posts to the server's log channel (D24).

### In the core

- **Handed-off applies, grants and outcomes,** above, over the audit log (D24).
- **`Diff.notes` through every door:** the core's plan reply and the adapters carry the notes beside the entries.
- Nothing else. Plans keep today's hash and stale rule (D21), and the queue is unchanged (D31).

### In the roles plugin

- **Four change actions.**
  - **`roles.give` and `roles.take`:** one role and up to ten named members, on every front door, slash commands among them. Manage Roles. No directory needed: the plan fetches the members live, so they work before a server's backfill. Ten changes take seconds, so they apply inside the core's apply job, as `roles.delete` does, and never wait behind a large change.
  - **`roles.give_matching` and `roles.take_matching`:** one role and a `MemberFilter`, on MCP, the service API and the site, since a whole filter has more fields than a slash command holds. Manage Roles and Manage Server, since a filter reads the directory as `admin.members` does.
  - A matching change is to present members only. `MemberFilter` has no name field, so no member can rename to enter or leave a change. Give adds "lacks the role", and take adds "has the role". At most 10,000 members, counted with the role condition; a larger change is refused with its count, so it is split, such as by join date.
- **Three to follow and undo matching changes:** `roles.list_changes`, the server's changes with their state and counts, a `READ`; `roles.stop`, which stops one between bursts, a `WRITE`, so a default token can stop a change; and `roles.revert`, which plans the opposite change over the members a change recorded as changed, destructive like the others, and checks each again as the job does. It is not exact: a member who already had a given role, on a directory a moment behind, counts as changed, since Discord answers both the same, so a revert can take away a role they had before. All need Manage Roles.
- **Names, and a click.** The pickers' `roles.add` and `roles.remove` keep their names. Each description says whether it changes a picker or members, and names its counterpart. In slash commands, `/roles add` beside `/roles give` stays a known cost, and so does a confirm button for giving even one member a role, since the destructive risk is what keeps a default token from changing roles.
- **On token doors, never a dangerous role.** Through MCP and the service API, a change refuses a role with a dangerous permission, giving or taking it, and each burst checks again, from the grant's door, so a role given Administrator after the apply stops the change. The dangerous set is the pickers' `DANGEROUS`, moved into the SDK beside `can_assign`. This is because an assistant confirms its own plans: a prompt-injected one could hand Administrator out, or strip Moderator from every moderator. Admins give such roles in Discord or on the site.
- **Destructive, so they plan first (D21).** A named change's entries are its members. A matching change's plan has one entry, the change itself: the role, with its permissions and position, give or take, and the filter, which is all that is hashed, so editing the role before confirm makes the plan stale, so members joining, leaving or renaming before confirm never make it stale. They were inside the filter the member agreed to. Its notes open with the change as a sentence, "Give Friends to present members who have Clan Member and lack Friends", so a swapped role and filter shows, and then the counts and a page of the members by name. The apply refuses, with a fresh plan, when the members it snapshots are more than a tenth above the planned count, carried unhashed in the diff, so a raid cannot grow a change unseen. Notes say what the role grants, when dangerous; how many match before the role condition, "3,000 match, 2,990 already have Friends"; the directory's state; how many of the members rank above the confirming member, since Discord does not compare targets' ranks; how long the change should take at the measured rate, which for thousands can be hours; the token's expiry, when it is sooner; and, when another change is running in the server, that this one waits behind it. 
- **A matching change runs as a job.** The apply takes the snapshot of the members the filter matches, at most 10,000, and stores, in one transaction, the change in the plugin's table `roles.role_changes`, with the role, give or take, the filter, the apply's audit row as its grant, the state, `next_at`, `started_at` and `progress_at`, and one row per member in `roles.role_change_members`: the change, the member as a `teabot.member_id`, and their outcome, pending until the job reaches them. It queues the server's `change` job, keyed per server, and returns `HandedOff`, naming the change, with `roles.list_changes` to follow it. The server's apply slot is free again at once, and no job payload holds the members.
- **The `change` job** works on the server's oldest unfinished change.
  - **One burst at a time, by claim.** A run claims the change with `UPDATE ... SET next_at = now() + interval '5 minutes' WHERE id = $1 AND next_at <= now() RETURNING ...`, and in the same transaction queues its own next run for then, so every exit, a crash or an unexpected error among them, leaves a run pending; a burst that ends normally moves it earlier. A run that claims nothing, because another is working or it came early, queues itself for `next_at` and exits.
  - **A short burst.** A change becoming the active one sets `started_at` and `progress_at`. Each run checks the grant with `ctx.authorized`, which returns the confirming member for `by=` and the door for the dangerous-role rule, and checks the next pending members against the directory, the filter and the role condition, reading the stored join method rather than searching again, so a member who no longer matches is marked skipped. It makes a few changes by ID, marking each row changed or gone, then, in one write, sets `progress_at` and `next_at` from the measured rate less headroom for pickers, and queues itself for `next_at`. The rate is the spike's constant; discord.py waits out a 429 if Discord's limit turns out lower, or many servers change roles at once. No worker waits between changes, and a restart or deploy resumes it.
  - **Stalled changes stop.** A run that finds the active change without progress for a day, such as after the plugin was off for weeks, stops it as "stalled". A day outlasts an outage, a failed deploy or a directory backfill, during which transient failures keep the change waiting.
  - **Failures.** `MemberGone` is marked and the run goes on. A transient failure, such as Discord's 5xx or a timeout, or `DirectoryUnavailable`, is caught: `next_at` moves a minute on, and the change waits. A permanent failure stops the change: `NotAuthorized`, the role refused, unknown or above the bot, or Forbidden. The job records "stopped" and why, and returns normally.
  - **When a change ends**, its counts come from its member rows, changed, gone, skipped and not reached; `ctx.record_outcome` puts them in the audit log, posted to the log channel, where an admin sees a stop such as an expired token; and the job goes on to the server's next unfinished change.
  - **Housekeeping:** when a change ends, the plugin deletes the server's changes, and their member rows, finished more than 30 days ago. No recurring job runs in the many servers using only pickers.
- **Member data (D11).** Each member row's member is a `teabot.member_id`, so a member's deletion deletes their rows. The confirming member's column is a `teabot.member_id`, which deletion would empty along with the change, so it is the one exception kept as the grant's audit row instead, whose user deletion already sets to 0: the next burst's `ctx.authorized` then stops the change and its outcome is recorded.
- **Revert's window** is the 30 days a finished change is kept.
- **Plugin reads are not audited.** `ctx.members` reads, unlike `admin.members` calls, are not look-ups in the audit log (D24); the plugin's actions that use them are.
- **Discord's invalid-request limit.** Discord bans an address after 10,000 401, 403 or 429 answers in ten minutes. A change stops on Forbidden, paces below the measured rate, and stops after a few 429s in a row; the spike also reads the rate-limit headers.
- **Fan-out.** Each change makes a member update, a row of directory history, and an `on_member_roles` job for each listening plugin: a change to 10,000 members is that many jobs per listener, paced by the change's rate. The plugin guide says so.
- **Its rate, measured (S10):** 10 changes per 10 seconds per server, so 10,000 members take close to three hours. A change paces itself at eight per 10 seconds, leaving two for picker presses. Whether a member still in membership screening can be given a role is not yet measured.
- **Pickers refuse a little more.** `roles.post` and `roles.add` check the member setting a picker up with `can_assign`, so one who lacks a role's minor permission, such as Create Events, cannot offer it; a press is checked for the bot only, as today. The changelog says so.
- **Disclosed.** `reads=["members"]` shows on the plugin's hub listing and site page, also to the many servers that use only its pickers.
- **Tokens.** A token's default maximum risk is `write` (D17), so an assistant needs a token made with `max_risk:destructive` to change roles. The docs say so.

### Not in the core

The core's admin tools read: the directory and the permission views. Changes to Discord belong to plugins, which a server turns on and off.

### One plugin, not two

Pickers and changes need the same permission, and an admin looks for both under "roles". They are separate modules in one package. The costs: a server cannot turn changes off while keeping pickers, and every server using pickers sees that the plugin reads the directory. Both need Manage Roles, and a token can be limited to some actions (D17), which covers assistants.

## Decisions this changes

When built:
- **D18** reaches deferred work, through `ctx.authorized` on the apply's audit row.
- **D21** gains notes on plans. A matching change runs after its apply ends, so the server's one apply slot covers the hand-off, not the hours of changes.
- **D24:** an apply that hands off records "handed off", its outcome follows as a linked row, and the Discord audit reason names the member a change is made for.
- **D29:** an action's input may be a model of D29 fields, flattened.
- **D45** gains `ctx.members`, `MemberFilter`, model inputs, `Diff.notes`, `HandedOff`, `by=`, changes by ID, `ctx.audit_id`, `ctx.authorized` and `ctx.record_outcome`.
