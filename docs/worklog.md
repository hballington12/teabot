# Work log

Each action taken while building teapot, and why. Newest last. Commits carry the detail; this records the reasons.

## 2026-11-13

- **Rewrote `main` and force-pushed.** The user asked to drop the PR-shaped history; the spike commit lost its "(#43)" suffix and got the local author. Trees were compared identical before the push.
- **WP1.2 settings and logging.** pydantic-settings with `SecretStr` secrets. A test keeps `template/teapot.env.example` in step with the `Settings` fields, so the template cannot drift.
- **Fixed `scripts/check.sh`.** Under `set -e`, `ruff check --fix` failed on unfixable lines before the formatter ran, so long lines were never wrapped. It now formats first and lets the fix step pass.
- **WP1.3 database layer.** Built to spike S1's findings: two login roles, plugin role switching with an explicit `RESET ROLE`, prepared-statement helpers, an explicit `tx`. Role names got a prefix setting because roles are server-wide and tests would otherwise collide with each other and with a dev instance.
- **asyncpg type aliases.** asyncpg's classes are generic only in its stubs, so `asyncpg.Connection[...]` fails at runtime. PEP 695 aliases in `teapot.db.types` are lazy and fix it in one place.
- **WP1.4 migration runner.** Added checksums for applied files, so an edited migration is refused. Corrected D2: bookkeeping tables such as `core.migrations` hold no server data and carry no `guild_id`.
- **WP1.5 locks and process rows.** A typed `Login` replaced loose connection keyword arguments, which strict pyright rejected. Database fixtures moved into the shared `tests/conftest.py` so there is one copy.
- **Installed ub-mode and its tools.** The user asked for ub-mode's principles. crapper, dryer and mutator were installed as editable uv tools under `~/.local/share/ub-tools`, siblings because mutator imports crapper from `../crapper`. `coverage` was added to the dev group so crapper does not pip-install into the uv environment.
- **WP1.6 work queue.** The queue was written before its tests, which broke TDD; crapper scored `claim` at 42. Tests brought every function under CRAP 10. Mutator then found 6 survivors out of 11:
    - notifying only for due jobs was a condition with no effect, so queuing now always notifies, in Python and in `schedule_job`
    - nothing tested that idle or failing workers wait between polls, or that a long job keeps its lease, so tests now do
  The mutation score went from 45.5% to 100%.
- **Added `scripts/quality.sh`, the glossary and this log**, as ub-mode asks.
- **Fixed the test databases' fixed names.** The first mutation pass on the older modules reported everything database-backed as uncovered. The cause was pytest-postgresql's template database `tests_tmpl`: a killed run left it behind and every later run failed with `DuplicateDatabase`. Names and role prefixes now carry the test process's pid, and a session fixture drops what dead runs left. This also lets mutator run four workers at once.
- **Spikes S3 and S4.** Run against the dev bot. Bulk overwrites keep command ids, so syncs do not use the daily create limit. Every interaction reaches `on_interaction` when no command tree is attached. Lazy member caching works with gateway search and REST fetches. No design change.
- **Planned WP1.7.** discord.py runs `setup_hook` after login and before shards connect, and `launch_shards` keeps a preset `shard_count`. The app fixes the shard count there and takes the shard locks before the gateway connects, the order D40 needs.
- **Mutation pass on WP1.2 to WP1.5.** With the test names fixed it gave real scores: pool 45.5%, processes 60%, cli 50%, the rest 83 to 93%. Responses:
    - **A real bug.** A non-superuser `REVOKE` on `set_config` gets a warning from Postgres, not an error, so `bootstrap` reported the revoke done when it was not, and `teapot init` would have told a managed-Postgres operator they were protected. It now checks `has_function_privilege('public', …)` after trying. Two tests with a real non-superuser owner caught it.
    - **Subtracted a distinction.** The app role's `INHERIT` changed nothing, because it is granted no roles. Both login roles are now `NOINHERIT`, and the parameter is gone.
    - **Modelled the scope.** A handle with an optional role made "core with a role" writable. `Database` is now the core handle and `PluginDatabase` adds the role switch, so the role checks are gone. The open-block check now applies to the core too, which has the same read-your-writes trap.
    - **Made timing testable.** A `Timing` value carries the slow threshold and an injectable clock, so the boundary is tested exactly. The cosmetic `round()` went.
    - **Missing tests:** JSON log attribute filtering, the formatter choice, a plugin without migrations, closing the lock connection, the 2³¹ boundary, `--admin-user` and the warning.
- **WP1.7 app runner.** Written test-first: maintenance, `/healthz` and `plugins list`, then the runner.
    - The health tests first used Starlette's `TestClient`, which runs the app on its own loop where asyncpg's connections do not work. They call the app in the test's loop instead, as production does.
    - crapper failed the first runner at CRAP 17.8 on untested orchestration. The orchestration moved into `runtime.py` over two small protocols and is tested with real pools, lock connection and workers and fake Discord and HTTP. `app.py` keeps only the real wiring.
    - Bugs found on the way:
        - the process row appeared a minute after start
        - a duplicate process served HTTP before finding its shard taken
        - uvicorn logged a traceback on shutdown, because its task was cancelled
        - an already-recorded failure re-raised during shutdown
        - text logs dropped the failure reason
        - uvicorn's colour copy of each message leaked into the logs
    - Mutator then removed two dead values: `shard_count or 1` and a placeholder count. `wait_for_shards()` and one future replace them.
    - Checked live: `teapot run` connected to the test server and reported healthy; a second process on the token stopped with exit 1 and one clear reason; SIGTERM gave a clean exit 0 with no process row left. close() after a failed login was checked against Discord with a bad token.
- **WP2.1 SDK types.** `teapot.sdk` now depends on nothing internal; the import contract forbids it. Plugins see the database and queue through SDK protocols the core implements. The plugin id rules moved from `db.naming` into the SDK, so they live in one place. Illegal values are refused where they enter: ref fields accept only 64-bit snowflakes (as ints or digit strings, strings in JSON); an `ActionSpec` cannot be destructive without a plan or misnamed; a `Manifest` refuses bad and reserved ids. The ref types first repeated their validator three times; the `Ref` marker now carries its own pydantic schema. Mutator found the 64-bit boundary untested.
- **WP2.2 loader.** Pure over candidates from entry points or a list, so tests need no packaging. Plugin locks are taken before migrating, so a purge cannot run underneath. A failing setup keeps nothing it registered. Wired into `teapot run`: the core and plugins migrate under the locks, statuses reach `/healthz` and the process row, and workers run jobs for loaded plugins. Mutator found three gaps: block-versus-failure logging, an object with a manifest but no setup, and a failed setup releasing its lock. A purge would otherwise have waited forever on a plugin that never loaded. typeshed's `EntryPoint.dist` is a class variable, so the loader reads it with `getattr`.
- **WP2.3 registry and call path.** `Registry.invoke` runs the plan's steps in order and audits refusals once as `refused`. `ctx.db` is bound to the server (`GuildPluginDatabase`), so `tx.schedule(...)` queues for that server in the same transaction through the plugin's own `schedule_job`. The SDK's `Row` became a minimal protocol, because asyncpg's `Record` is not a `Mapping` in its stubs. dryer found the transaction's and the handle's `schedule` identical; one `ServerScheduling` mixin replaced both. A mutator "uncovered" line was again a continuation line of a multi-line call; `--no-coverage` confirmed the new test kills it.
- **WP2.4 audit log.** Migration 0002 adds `core.audit_log` and the day-partitioned `core.audit_reads` with a default partition, so an insert never fails for want of a partition. Partition upkeep needs the parent's owner, so it goes through two `SECURITY DEFINER` functions and the app role stays unprivileged; a day whose rows already sit in the default partition is skipped rather than failing. A change's outcome and its `post_audit` job share one transaction (`Queue.schedule(within=tx)`). The log channel lives in `AdminConfig` from the start, so the setting has one home. Mutator found that a refused lookup was being posted, which D24 rules out; rows are now routed by risk alone. Two tests had hardcoded the core schema at version 1; they now derive it from the migration files.
- **WP2.6 schema builder.** The field rules of D29 belong to the protocol, so they live in `teapot.sdk.inputs`, and `ActionSpec` refuses an unsupported field when it is built; an illegal input model cannot be written, and the loader reports it as a failed setup with no extra code. `adapters/schema.py` only maps the classification onto Discord's command JSON and the MCP schema. Mutator showed the "was it optional" flag repeated what pydantic already knows from the default, so it went, and that a two-type union would have been accepted as its first type; a test now refuses it.
- **WP2.7 wiring.** The router reaches the running bot through `TeapotClient.on_interaction`. The registry gets the real audit log; plugin jobs run with a server-bound context and must belong to a server. Pyright caught that a server-less handle would break the SDK's `Db` contract. Until WP3.2's per-server sync, development bulk-registers every command group in `TEAPOT_DEV_GUILD_ID`. Unsubmitted modal drafts are pruned daily. **Design change:** plugin buttons and select menus moved from D6's "from the start" list to deferred work. No planned plugin needs them yet, and their right shape is now clear: a component routes to an action, so a press gets the one call path's permission check and audit (D1). The guard refused two heredoc appends, which left tests unwritten; mutator's survivors pointed straight at the missing coverage.
- **WP2.8 testing helpers.** `teapot.testing` ships the fakes, the Postgres fixtures and a `PluginHarness` that loads a plugin through the real loader and migrations and invokes it through the real call path. The core's own fixtures moved there, and the registry tests dropped their private fakes, so plugin authors and the core test the same way. The pytest pieces are a `teapot[testing]` extra. Mutator found the REST-only member path unused by the harness tests, and that autocommit was each caller's job; `cleanup` now sets it itself. dryer found the two dead-run finders alike; one helper serves both.
- **WP2.9 first plugins.** `teapot-announcements` posts an embed. `teapot-devtools` exercises its own table, the core's refusal of plugin roles, and a failing setup. `teapot-devtools-twin` declares `devtools` again, in an opt-in group for the exit check. Writing announcements showed plugins had no way to tell a member what went wrong, so the SDK gained `ActionError`. The fixtures moved to `-p teapot.testing.fixtures` so plugin tests share them; as a plugin they lost a name clash with pytest-postgresql's own `postgresql` fixtures, and got their own names (`teapot_pg`, `teapot_pg_server`). Mutator found:
    - no test of a channel that takes no messages, so `teapot.testing` gained `FakeVoiceChannel`
    - an untestable "core was readable" branch in devtools, which now raises, since that would mean isolation is broken
    - an untested cached-member default
  The quality gates now cover `plugins/` too.
- **WP2.10 authoring guide.** `docs/plugin-authoring.md` covers the package, actions and input types, the database rules (one statement per call, `tx` inside blocks, nothing slow inside a block, no dynamic SQL from member input), migrations, config, jobs safe to run twice, `ActionError`, testing with `teapot_harness`, and the review checklist the new PR template repeats. Its examples use only names that exist in the SDK today.
