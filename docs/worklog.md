Each action taken while building teapot, and why. Newest last. Commits carry the detail; this records the reasons.

- **WP2.1 SDK types.** `teapot.sdk` now depends on nothing internal; the import contract forbids it. Plugins see the database and queue through SDK protocols the core implements. The plugin id rules moved from `db.naming` into the SDK, so they live in one place. Illegal values are refused where they enter: ref fields accept only 64-bit snowflakes (as ints or digit strings, strings in JSON); an `ActionSpec` cannot be destructive without a plan or misnamed; a `Manifest` refuses bad and reserved ids. The ref types first repeated their validator three times; the `Ref` marker now carries its own pydantic schema. Mutator found the 64-bit boundary untested.
- **WP2.2 loader.** Pure over candidates from entry points or a list, so tests need no packaging. Plugin locks are taken before migrating, so a purge cannot run underneath. A failing setup keeps nothing it registered. Wired into `teapot run`: the core and plugins migrate under the locks, statuses reach `/healthz` and the process row, and workers run jobs for loaded plugins. Mutator found three gaps: block-versus-failure logging, an object with a manifest but no setup, and a failed setup releasing its lock. A purge would otherwise have waited forever on a plugin that never loaded. typeshed's `EntryPoint.dist` is a class variable, so the loader reads it with `getattr`.
- **WP2.3 registry and call path.** `Registry.invoke` runs the plan's steps in order and audits refusals once as `refused`. `ctx.db` is bound to the server (`GuildPluginDatabase`), so `tx.schedule(...)` queues for that server in the same transaction through the plugin's own `schedule_job`. The SDK's `Row` became a minimal protocol, because asyncpg's `Record` is not a `Mapping` in its stubs. dryer found the transaction's and the handle's `schedule` identical; one `ServerScheduling` mixin replaced both. A mutator "uncovered" line was again a continuation line of a multi-line call; `--no-coverage` confirmed the new test kills it.
- **WP2.4 audit log.** Migration 0002 adds `core.audit_log` and the day-partitioned `core.audit_reads` with a default partition, so an insert never fails for want of a partition. Partition upkeep needs the parent's owner, so it goes through two `SECURITY DEFINER` functions and the app role stays unprivileged; a day whose rows already sit in the default partition is skipped rather than failing. A change's outcome and its `post_audit` job share one transaction (`Queue.schedule(within=tx)`). The log channel lives in `AdminConfig` from the start, so the setting has one home. Mutator found that a refused lookup was being posted, which D24 rules out; rows are now routed by risk alone. Two tests had hardcoded the core schema at version 1; they now derive it from the migration files.
- **WP2.6 schema builder.** The field rules of D29 belong to the protocol, so they live in `teapot.sdk.inputs`, and `ActionSpec` refuses an unsupported field when it is built; an illegal input model cannot be written, and the loader reports it as a failed setup with no extra code. `adapters/schema.py` only maps the classification onto Discord's command JSON and the MCP schema. Mutator showed the "was it optional" flag repeated what pydantic already knows from the default, so it went, and that a two-type union would have been accepted as its first type; a test now refuses it.

Until WP3.2's per-server sync, development bulk-registers every command group in `TEAPOT_DEV_GUILD_ID`. Unsubmitted modal drafts are pruned daily. **Design change:** plugin buttons and select menus moved from D6's "from the start" list to deferred work. No planned plugin needs them yet, and their right shape is now clear: a component routes to an action, so a press gets the one call path's permission check and audit (D1). The guard refused two heredoc appends, which left tests unwritten; mutator's survivors pointed straight at the missing coverage.

- **WP3.1 admin plugin.** `/plugins list | enable | disable | config` and `/audit channel | recent`. The registry now takes action sources instead of loaded plugins, so a built-in group needs no manifest, schema or enablement row, and a plugin's database opens only when an action uses it. The first cut named everything `/admin ...`; the plan has `/plugins` and `/audit` as their own commands, so each group became its own source and `plugins`, `audit` and `tokens` joined the reserved ids. Dryer caught the unknown-plugin check written twice. Mutator found an untested default: a newly installed plugin with no row here lists as disabled.
- **WP3.2 command sync.** `core.command_sync` holds a hash of the command set Discord last accepted for each server, with row 0 for the global set. `sync_commands` jobs work out the set when they run, send one bulk overwrite only when the hash differs, and save it only after Discord accepts. Enabling or disabling queues one; startup queues only the servers whose set changed, which also covers plugin upgrades. The admin groups are global, and development registration and `TEAPOT_DEV_GUILD_ID` are gone. Writing the global sync as a job with no server exposed a queue bug: a shard filter could never claim such a job, which would have stranded daily maintenance once processes run some shards each. Mutator asked for the hash to be pinned as independent of key order.
- **WP3.3 plugin purge.** `teapot plugins purge <id>` takes the plugin's advisory lock exclusively, shows what goes, and in one transaction drops the schema and role and the plugin's core rows, queues command syncs and writes audit rows. Those rows go to every server that had the plugin, which the log channel shows as "the operator", plus row 0 for the instance. Two things the design left implicit had to be pinned. A non-superuser owner holds plugin roles without inheriting them, so it counts rows and drops the schema through `SET ROLE`; a test runs the whole purge as such an owner, since the test superuser would hide that. And reserved ids are refused, because `plugins purge core` would otherwise delete the core's own migration rows.
- **WP3.4 guild removal.** Join and remove events, and a comparison at `on_ready`, keep `core.guilds` current. Removal starts the grace period and queues `purge_guild`; a second removal event changes nothing. A return within the grace period cancels the purge and resumes the jobs, and a command sync sends the commands again, since removal forgets the stored hash. `purge_guild` deletes the server's rows from every plugin schema as that plugin's role, then from every core table with a `guild_id`, its own job row included. That keeps it repeatable, and tables added later are covered without edits. Two design points needed pinning. The startup comparison looks only at this process's shards, or one process of several would mark the others' servers removed. A purge for a server that came back deletes nothing.

- **S5 MCP low-level server.** `mcp` 2.3.0 does everything D28 asks of it: per-token tool lists, annotations, instructions, and bearer auth without an OAuth server. A subagent mapped the SDK source, and a spike then checked each finding over HTTP. - **WP4.1 tokens.** `core.tokens`, `teapot.auth.tokens` (issue, check, list, revoke; only the SHA-256 of the secret is stored; `last used` written at most once a minute), the `BearerTokens` middleware for `/mcp` and `/api`, and `/tokens create | list | revoke`. The registry now checks three more things before the live permission check: the front door against the action's surfaces, the token's maximum risk, and its allow-list. So a token can never reach a slash-only action such as `/plugins enable`. Wiring the token commands into both `teapot run` and the harness would have made a third copy of the core's wiring, so `teapot.assembly.assemble` now builds it once for both. `teapot.testing` gained `invoke_with_token`. The token commands showed that the SDK's input check could not see through `type` aliases, and now it does. The default-lifetime test caught an expiry taken from the Python clock against a `created_at` from the database's, so expiry is now computed in SQL.
- **WP4.2 admin lookups.** `admin.describe_guild` (channels the member can see and roles, 50 a page), `admin.find_members` (gateway search, up to 100) and `admin.job_status` (its starter, or Manage Server), on every surface. The fakes now take the shape of discord.py's: `FakeGuild.channels` is a list, as `Guild.channels` is, and channels have names and per-member visibility. Roles, nicknames and `query_members` are new. The member lookup moved into `find_member`, which the permission check and `describe_guild` share. asyncpg hands back `jsonb` as text, since the pools register no JSON codec, so the job's progress is parsed where it is read.
- **WP4.3 MCP adapter.** `/mcp` serves the low-level server behind `BearerTokens`, stateless with JSON responses, as S5 found. The tool list is built for each token; calls go through the one call path; refusals and failures return as `isError`; `UntrustedText` becomes an `untrusted_text` marker that JSON escaping keeps intact. uvicorn's lifespan is now on, because the session manager must be entered and left in one task. The tests first held it in a pytest fixture, which anyio refused because pytest-asyncio tears fixtures down in another task. Tool names and the action names in allow-lists stay distinct (`announcements_post` against `announcements.post`), and a slash-only action is simply no tool. A live smoke test against the dev bot answered 401 without a token and listed four tools with one.
- **WP4.4 service API.** `POST /api/v1/actions/<name>` runs an action for a backend through the one call path, as the token's member. Refusals map onto statuses a backend can act on, and outputs are plain JSON with no untrusted markers, since no LLM reads them. The live smoke test found a gap: `/healthz` said ok as soon as the shards connected, before the guild cache had filled, so a token call in that window was refused as `not_in_guild`. `/healthz` now reports shards as down until the client is ready.

- **WP6.1 plans.** The SDK gained `Diff` and `DiffEntry`, which a `plan` returns, and `ActionContext.report`, an apply's progress. `teapot.core.plans` owns the destructive call path behind the registry's `PlanBook` protocol, so neither module imports the other.
