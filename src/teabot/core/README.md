# teabot.core

- `processes.py`: the lock connection with shard and plugin advisory locks, reading loaded plugins from `pg_locks`, and the informational process row (D40, spike S2).
- `queue.py`: the durable work queue (D31): `NewJob`, claims with `SKIP LOCKED` and leases, the computed shard filter, retries with back-off.
- `worker.py`: worker pools that run claimed jobs, keep their leases, and sleep until woken by `NOTIFY` or the next due job.
- `maintenance.py`: the daily `core.maintenance` job: prunes finished jobs and stale process rows in batches.
- `loader.py`: the plugin loader (D14, D46): entry points or a given list, unique ids, disabled plugins, plugin locks, migrations and setup, with a status and reason for every plugin.
- `config.py`: per-server plugin config (D8, D10), validated through the plugin's current model, with a `ConfigError` naming plugin and server when stored config no longer validates.
- `registry.py`: the action registry and its one call path (D1, D18, D19, D24): server, enabled plugin, config, input, live permissions, audit, run, outcome.
- `command_sync.py`: per-server command sync (D32). Admin commands are global; a plugin's group is a guild command only where it is enabled. `sync_commands` jobs compare a hash with `core.command_sync` and save it only once Discord accepts the overwrite. Startup queues only what changed.
- `plans.py`: plan then apply (D21). A destructive call without `confirm` stores its diff's canonical hash on a `planned` audit row with a random confirm value. A call with `confirm` must come from the same member, for the same server, action and input, within 15 minutes, on an unused plan, and with an unchanged diff, or it gets a fresh plan marked stale. It then queues the core `apply` job, which runs once, checks the member again and reports progress.
- `lifecycle.py`: plugin purge (D7) and guild removal (D49). Guild removal starts a grace period of `TEABOT_GUILD_RETENTION_DAYS`, which pauses the server's jobs and queues `purge_guild`. A return within it cancels the purge. Startup compares the gateway's servers with `core.guilds`, on this process's shards only. Plugin purge: It takes the plugin's lock exclusively and refuses while any process has the plugin loaded. It shows the rows it will delete and asks first. One transaction then drops the schema as the plugin's role, drops the role, deletes the plugin's core rows, queues command syncs and audits the purge for each server and the instance. It needs no plugin code.
- `audit.py`: the audit log (D24): started and finished change rows with their post queued in the same transaction, one row per lookup in the day-partitioned reads table, posts to the log channel, and retention.
- `directory/`: the member directory (D55). `gateway.py` wraps discord.py's member parsers, `writer.py` holds one writer per shard and `apply.py` its diff, history and plugin events, `reconcile.py` pages Discord's member list through the writer, `joins.py` reads join methods from Discord's member search, `query.py` turns filters into SQL, and `service.py` wires them together with retention.
- `events.py`: Discord events for plugins (D6), as jobs, with late events for handlers that ask (D55).
